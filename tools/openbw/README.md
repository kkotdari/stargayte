# OpenBW 헤드리스 덤퍼 (실현 가능성 확인 완료)

리플레이를 **유추하지 않고 실제로 시뮬레이션**해서, 프레임마다 유닛의 참값을 뽑는다.
지금 우리 파이프라인(커맨드 증거 → 정체 유추 → 원장 결합 → 자체 시뮬)이 하는 일을
통째로 대신할 수 있는 자리다.

## 확인된 것

* OpenBW는 **헤더 온리 C++**다(`bwgame.h` 800KB + `replay.h`). BWAPI도 SDL도 필요 없다.
* 맥(Apple clang 21, arm64)에서 **한 번에 빌드된다** — 963KB 실행 파일, 의존성 0.
* 시뮬에 실제로 필요한 자료는 **파일 열 개**뿐이다(그림·소리는 한 장도 안 쓴다):

  ```
  arr/units.dat      arr/weapons.dat   arr/upgrades.dat  arr/techdata.dat
  arr/flingy.dat     arr/sprites.dat   arr/images.dat    arr/orders.dat
  arr/images.tbl     scripts/iscript.bin
  ```

  합쳐 2MB 남짓이다. MPQ 셋(Patch_rt·BrooDat·StarDat)을 그대로 가리켜도 되고, 위
  열 개만 풀어 둬도 된다 — 덤퍼가 둘 다 받는다.
* 지도는 리플레이 안에 들어 있다. 따로 안 필요하다.

## 빌드

```
git clone --depth 1 https://github.com/OpenBW/openbw
clang++ -std=c++17 -O2 -w -I openbw -o bwdump bwdump.cpp
```

## 실행

```
./bwdump <자료폴더> <리플레이.rep> [프레임간격]     # 자료폴더 = 스타 설치 폴더 또는 풀어 둔 폴더
```

프레임·유닛마다 `id owner type x y hp shield energy completed`를 탭으로 내보낸다.
이것이 곧 지금 `SimTrack`이 담는 것과 같은 내용이고, 다른 점은 **어림이 아니라 참값**이라는
것뿐이다.

## 남은 일

1. 자료 열 개(또는 MPQ 셋)를 구해 한 판 돌려 본다 — 여기서 막혀 있다.
2. 지금 파이프라인과 대조한다: 정체 판정·원장 결합률·죽음 판정이 실제로 몇 %를 맞히나.
   지금까지 이 프로젝트에는 **정답표가 없었다** — 이 대조가 처음으로 그것을 만든다.
3. 결과가 확실하면 분석 시각에 서버에서 한 번 돌려 트랙을 굽고, 웹앱은 그대로 둔다.

## 자료 파일과 법 — 반드시 지킬 선

이 열 개는 블리자드 저작물이다. 스타크래프트가 무료로 배포된다는 것과, 그 안의 파일을
**우리가 퍼뜨려도 된다**는 것은 전혀 다른 말이다. 선은 하나다 — **읽는 것과 뿌리는 것.**

* ✅ **제 기계에서 제 설치본을 읽는 것** — 문제 없다. OpenBW·BWAPI·Titan Reactor를 비롯한
  모든 도구가 이 전제로 돈다(그래서 하나같이 "스타를 설치하고 그 폴더를 가리켜라"라고
  적혀 있다). 우리 bwextract·bwdump도 그 자리에 선다.
* ⛔ **저장소에 커밋** — 절대 안 된다. `.gitignore`로 막아 둔다.
* ⛔ **클라이언트로 내려보내기** — WASM 번들에 2MB를 실어 브라우저에 주는 방식(위 (b))은
  명백한 재배포다. 쓰지 않는다.
* ⚠ **서버에 두기** — 밖으로 노출하지 않아도 복제본을 보유하는 것은 맞다. 회색지대다.

### 고른 길 — 서버에 두되, 밖으로는 한 바이트도 안 나간다

운영자 기계에서만 돌리는 안은 운영이 안 된다(등록이 폰·남의 PC에서도 일어난다). 그래서
자료를 **서버에** 둔다. 회색지대인 것은 맞으므로, 위험을 낮추는 다섯 줄을 규칙으로 박는다:

1. **저장소·배포 아티팩트에 안 넣는다.** `.gitignore`로 막았고, 이미지 빌드에도 안 담는다 —
   서버에 손으로 두거나 비공개 저장소에서 부팅 때 내려받는다.
2. **정적 서빙 경로 밖에 둔다.** 어떤 API도 이 파일을 돌려주지 않는다. 웹에서 이 파일에
   닿는 길이 **하나도 없어야** 한다.
3. **나가는 것은 결과뿐이다.** 트랙(좌표·체력·명령)은 계산해 낸 사실이지 저작물의 복제가
   아니다. 클라이언트는 예나 지금이나 트랙만 받는다.
4. **운영자가 정품을 보유한다.** 서버의 복제본은 그 한 벌의 사본이라는 자리에 선다.
5. **최소한만 둔다.** 그림·소리·영상이 든 통짜 MPQ가 아니라 bwextract가 뽑은 **열 개(2MB)**만.

(법률 자문이 아니다. "읽기는 되고 뿌리기는 안 된다"는 선은 이 바닥에서 오래 지켜져 온
관행이고, 위 다섯 줄은 그 선 안쪽에 머물기 위한 실무 조치다. 판단과 책임은 운영자 몫이다.)

### 서버 파이프라인 (붙일 자리)

지금은 등록할 때 **브라우저 워커**가 `.rep`을 읽어 트랙을 굽고 그것을 저장한다
(`replaySummaryWorker` → `POST /api/game-results/:id/unit-tracks`). OpenBW는 그 굽는 일을
서버로 옮긴다:

```
업로드된 .rep  →  bwdump <자료폴더> <rep>  →  트랙으로 접기  →  저장
```

* `bwdump`는 리눅스 정적 바이너리로 빌드해 서버에 둔다(의존성이 없어 그대로 된다).
* 브라우저 쪽 분석은 **폴백으로 남긴다** — 서버가 못 돌 때와 옛 저장본을 위해.
* 백엔드 코드는 이 저장소에 없다. 붙이는 자리는 `/api/game-results/:id/unit-tracks`를
  받는 그 서비스다.

### 마지막으로 뚫은 것 — 리마스터의 유닛 태그와 **그릇 크기**

명령이 가리키는 유닛을 못 찾아 **고르기가 늘 빈손**이었다. 그러면 명령은 다 실행되는데
아무 일도 안 일어난다.

옛 태그는 `(index+1) | (generation << 11)`인 16비트였다. 리마스터는 32비트로 넓히면서
index 칸을 **13비트**로 늘렸다:

```
리마스터 태그 = (index + 1) | (generation << 13)
```

처음에는 여기에 `+1700`을 더해야 맞는 줄 알았다. 아니었다. 그 1700은 **그릇 크기 차이**다.

#### LMTS — 리마스터는 한도를 두 배로 늘렸다

요즘 리플레이(1.21+)에는 `LMTS`라는 구획이 있고, 그 안에 그릇 크기가 그대로 적혀 있다.
`xxd`로 읽어 보면 uint32 일곱 개다:

| 그릇 | 리마스터(LMTS) | OpenBW(1.16.1) |
|---|---|---|
| 이미지 | 10000 | 5000 |
| 스프라이트 | 5000 | 2500 |
| thingy | 1000 | 500 |
| **유닛** | **3400** | **1700** |
| 총알 | 400 | 100 |
| 명령(order) | 4000 | 2000 |
| 안개 스프라이트 | 1000 | — |

브루드워는 유닛 자리 번호를 `그릇크기 − 몇째로 만들어졌나`로 매긴다. 그래서 그릇이
1700칸이면 첫 유닛이 1699번, 3400칸이면 3399번이다 — **모든 번호가 정확히 1700씩 어긋난다.**
내가 억지로 더하던 `+1700`이 바로 그 차이였다.

이걸 상수 보정으로 때우면 유닛이 1700칸을 넘는 순간(무한 지도는 미네랄 덩이만 1556개다)
번호가 한 바퀴 돌아 어긋나기 시작한다. 그래서 보정이 아니라 **그릇을 3400칸으로 넓히는**
쪽으로 고쳤다(`bw_limits`, 요즘 리플레이일 때만).

같이 넓혀야 하는 곳이 하나 더 있다 — 엔진 **속**에서도 유닛을 16비트 id로 가리킨다
(수송선 탑승 명부 `loaded_units`, 길찾기의 `last_collision_unit`, 단축키 묶음). 그쪽
index 칸이 11비트라 1700을 넘는 번호가 잘린다. `unit_id_t`에 index 폭을 매개변수로 주고
내부용은 13비트짜리 32비트 id를 쓰게 했다.

**어떻게 알아냈나.** 같은 지도(UGL 17 Anti-Hack)의 1.16 판과 리마스터 판을 나란히 돌려
태그 차이가 늘 7844(= 1700 + 3·2048)임을 보고 식을 세웠다. 그 뒤 리플레이마다 적중률이
시간이 갈수록 무너지는 것을 쫓다가, 못 찾은 태그의 index가 **1041~1755**로 우리가 가정한
범위(1701~3400) 아래라는 것을 보고 규약이 아니라 그릇이 문제임을 알았다. `LMTS`가 그것을
확인해 주었다.

공식 문서에는 이 식이 없다 — screp·jssuh 같은 파서는 태그를 **읽어 넘기기만** 하지 그것이
어느 유닛인지는 안 따지기 때문이다(그럴 필요가 없다). 시뮬레이터만이 이걸 알아야 한다.

### 진짜 원인 — **팀전인데 동맹을 안 걸고 있었다**

리마스터 판이 시간이 갈수록 무너지고 1.16 판만 멀쩡한 것을 두고 오래 헤맸는데, 비교
자체가 잘못돼 있었다. 가진 1.16 리플레이는 **게임 갈래 2(멜리)**, 리마스터 다섯 판은
전부 **게임 갈래 15(Top vs Bottom)** — 즉 "리마스터 대 레거시"가 아니라 **개인전 대 팀전**이었다.

팀전은 같은 편끼리 **동맹으로 시작한다.** OpenBW의 리플레이 설정은 그걸 안 걸어서, 우리
시뮬에서는 한 편이 서로 적이었다. 그래서 만나자마자 아군끼리 치고받았고 — 없던 전투다 —
죽는 유닛이 달라지자 유닛 자리(슬롯) 재활용이 어긋나고, 그 뒤 명령이 통째로 헛돌았다.
"3분 반까지는 완벽하다"던 것은 그저 **양 편이 아직 안 만났을 뿐**이었다.

고침(`replay.h`): 갈래 11·12·13·15면 같은 편끼리 `alliances`와 `shared_vision`을 건다.
시야 공유도 필요하다 — 안 걸면 8인전이 56.3%에서 33.6%로 떨어진다.

| 리플레이 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 151231 (1.16 · 멜리 5인) | 99.7% | 99.7% |
| 251108 (3v3) | 58.6% | **99.9%** |
| SG_26081613330800 (2v2) | 55.5% | **99.9%** |
| SG_26081623590300 (3v3) | 53.1% | **99.9%** |
| DJKisoo (3v2 · 24분) | 29.1% | 82.8% |
| Super빠른무한 BT (4v4 · 31분) | 24.4% | 56.3% |

### 발키리 로켓 문턱도 한도를 따라간다

`create_bullet`에 발키리 로켓만 걸리는 붙박이 문턱 `active_bullets_size >= 80`이 있다.
원판 총알 그릇 100칸의 8할이다. 리마스터 그릇은 400칸이니 문턱도 320이어야 한다.
80으로 두면 발키리가 실제보다 덜 쏴서 그 판의 전투가 갈린다 — 발키리가 나오는 24분짜리
판에서 78.0% → 82.8%.

### 남은 것 — 긴 무한 판 두 개

`DJKisoo`는 16분까지, `Super빠른무한 BT`는 11분까지 **분마다 100%**다. 그 뒤로 무너진다.
씨앗은 아주 작다 — 우리가 유닛을 0.2~2초 늦게 만들거나, 1.6초 일찍 죽인다. 자리와 세대는
정확히 같으니 **구조가 아니라 시각**이 어긋난다. 한 번 어긋나면 생산 명령이 튕기고
(`build:고른게없다`) 눈덩이가 된다: 늦는 양이 12분 5초 → 13분 56초 → 15분 98초로 커진다.
유닛·스프라이트·이미지·총알·명령·thingy 그릇은 하나도 안 찬다(계수기로 확인).

## 트랙 뽑기 — 앱이 먹는 꼴로

```
node scripts/openbw-tracks.mjs <리플레이.rep> [--out 트랙.json] [--step 3]
```

`bwdump --tracks`가 프레임마다 유닛의 자리·방향·상태를 내고, 스크립트가 그것을 앱의
`SimTrack` 꼴로 접는다. 상태 번호는 앱과 같다(0 가만 1 이동 2 안에 탐 3 사라짐 4 싸움
5 채취 6 파묻힘 7 미네랄 들고 8 가스 들고).

키는 **곧게 가는 동안 안 적는다** — 직전 표본이 '적은 점 → 지금'을 잇는 선에서 얼마나
벗어나는지 보고 벗어날 때만 꺾임점을 남긴다. 그냥 다 적으면 14분짜리가 240만 줄인데
19만 줄로 줄고, 레거시 시뮬이 내던 12만 개와 같은 급이다. 곱기는 `BWDUMP_DEV`(픽셀)와
`BWDUMP_HEAD`(0~255)로 조절한다.

지도가 놓아 준 자원(미네랄·가스)은 트랙에서 뺀다 — 앱은 그것을 지도에서 그리고, 경기
하나에 400~1556개라 그냥 두면 짐의 절반이 그것이다.

| 리플레이 | 트랙 | 키 | 32비트 실수로 | 믿을 수 있는 구간 |

### 막힌 한 자리 — 고르기가 아무도 못 집는다

명령이 가리키는 유닛 태그를 시뮬이 못 찾는다. 그래서 선택이 늘 비고, 선택이 비니 생산도
건설도 이동도 **하나도 일어나지 않는다**(유닛 수가 800초 내내 시작 그대로다).

숫자로 좁힌 자리:

* 첫 고르기(프레임 2)의 태그는 `0x26cd`·`0x26ce`처럼 **잇따른 값**이다 → 낮은 비트가
  index인 것은 맞다(한 사람의 일꾼 넷이 잇따라 만들어졌다는 뜻).
* 11·12·13비트 어느 폭으로 갈라도 index는 **1741**로 같다.
* 그런데 우리 시뮬의 유닛은 index 0~1699에 있고, 첫 일꾼들은 index 22~25다.
* 지도가 선언한 유닛 1650 + 시작 유닛 38 = 1688로도 1741에 못 미친다 — 실제 게임은
  그 앞에 **쉰 남짓을 더** 만들었다는 뜻이다.

곧 **유닛을 만드는 차례가 실제 게임과 어긋난다.** OpenBW가 옛 리플레이를 제대로 재생하는
것을 보면 옛 게임과는 맞는 차례이므로, 리마스터가 시작 때 무언가를 더 만들거나 다른
차례로 만든다고 보는 것이 옳다. 1v1 리플레이에서도 똑같이 막히므로 지도 크기 문제는 아니다.

다음에 볼 것:
1. 리마스터가 시작 때 더 만드는 것이 무엇인가 — 라바·맵 공개용 유닛·시작 지점 처리 차례.
2. 32비트 태그의 index/generation 나눔이 옛것과 정말 같은가(0x26cd는 옛 규약의 유효
   범위 밖이다 — 세대 4의 유효 구간이 8193~9892인데 9933은 그 밖이다).
3. 옛 형식 리플레이 한 판을 구해 대조 — 지금 막힌 것이 리마스터 탓인지 아닌지 단번에 갈린다.
