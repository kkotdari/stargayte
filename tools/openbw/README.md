# OpenBW 헤드리스 덤퍼 (실현 가능성 확인 완료)

리플레이를 **유추하지 않고 실제로 시뮬레이션**해서, 프레임마다 유닛의 참값을 뽑는다.
지금 우리 파이프라인(커맨드 증거 → 정체 유추 → 원장 결합 → 자체 시뮬)이 하는 일을
통째로 대신할 수 있는 자리다.

## 확인된 것

* OpenBW는 **헤더 온리 C++**다(`bwgame.h` 800KB + `replay.h`). BWAPI도 SDL도 필요 없다.
* 맥(Apple clang 21, arm64)에서 **한 번에 빌드된다** — 963KB 실행 파일, 의존성 0.
* 시뮬에 실제로 필요한 자료는 **파일 열 개**뿐이다(그림·소리는 한 장도 안 쓴다):

  ```
  arr/units.dat      arr/weapons.dat   arr/upgrades.dat  arr/techdata.dat
  arr/flingy.dat     arr/sprites.dat   arr/images.dat    arr/orders.dat
  arr/images.tbl     scripts/iscript.bin
  ```

  합쳐 2MB 남짓이다. MPQ 셋(Patch_rt·BrooDat·StarDat)을 그대로 가리켜도 되고, 위
  열 개만 풀어 둬도 된다 — 덤퍼가 둘 다 받는다.
* 지도는 리플레이 안에 들어 있다. 따로 안 필요하다.

## 빌드

```
git clone --depth 1 https://github.com/OpenBW/openbw
clang++ -std=c++17 -O2 -w -I openbw -o bwdump bwdump.cpp
```

## 실행

```
./bwdump <자료폴더> <리플레이.rep> [프레임간격]     # 자료폴더 = 스타 설치 폴더 또는 풀어 둔 폴더
```

프레임·유닛마다 `id owner type x y hp shield energy completed`를 탭으로 내보낸다.
이것이 곧 지금 `SimTrack`이 담는 것과 같은 내용이고, 다른 점은 **어림이 아니라 참값**이라는
것뿐이다.

## 남은 일

1. 자료 열 개(또는 MPQ 셋)를 구해 한 판 돌려 본다 — 여기서 막혀 있다.
2. 지금 파이프라인과 대조한다: 정체 판정·원장 결합률·죽음 판정이 실제로 몇 %를 맞히나.
   지금까지 이 프로젝트에는 **정답표가 없었다** — 이 대조가 처음으로 그것을 만든다.
3. 결과가 확실하면 분석 시각에 서버에서 한 번 돌려 트랙을 굽고, 웹앱은 그대로 둔다.

## 자료 파일과 법 — 반드시 지킬 선

이 열 개는 블리자드 저작물이다. 스타크래프트가 무료로 배포된다는 것과, 그 안의 파일을
**우리가 퍼뜨려도 된다**는 것은 전혀 다른 말이다. 선은 하나다 — **읽는 것과 뿌리는 것.**

* ✅ **제 기계에서 제 설치본을 읽는 것** — 문제 없다. OpenBW·BWAPI·Titan Reactor를 비롯한
  모든 도구가 이 전제로 돈다(그래서 하나같이 "스타를 설치하고 그 폴더를 가리켜라"라고
  적혀 있다). 우리 bwextract·bwdump도 그 자리에 선다.
* ⛔ **저장소에 커밋** — 절대 안 된다. `.gitignore`로 막아 둔다.
* ⛔ **클라이언트로 내려보내기** — WASM 번들에 2MB를 실어 브라우저에 주는 방식(위 (b))은
  명백한 재배포다. 쓰지 않는다.
* ⚠ **서버에 두기** — 밖으로 노출하지 않아도 복제본을 보유하는 것은 맞다. 회색지대다.

### 고른 길 — 서버에 두되, 밖으로는 한 바이트도 안 나간다

운영자 기계에서만 돌리는 안은 운영이 안 된다(등록이 폰·남의 PC에서도 일어난다). 그래서
자료를 **서버에** 둔다. 회색지대인 것은 맞으므로, 위험을 낮추는 다섯 줄을 규칙으로 박는다:

1. **저장소·배포 아티팩트에 안 넣는다.** `.gitignore`로 막았고, 이미지 빌드에도 안 담는다 —
   서버에 손으로 두거나 비공개 저장소에서 부팅 때 내려받는다.
2. **정적 서빙 경로 밖에 둔다.** 어떤 API도 이 파일을 돌려주지 않는다. 웹에서 이 파일에
   닿는 길이 **하나도 없어야** 한다.
3. **나가는 것은 결과뿐이다.** 트랙(좌표·체력·명령)은 계산해 낸 사실이지 저작물의 복제가
   아니다. 클라이언트는 예나 지금이나 트랙만 받는다.
4. **운영자가 정품을 보유한다.** 서버의 복제본은 그 한 벌의 사본이라는 자리에 선다.
5. **최소한만 둔다.** 그림·소리·영상이 든 통짜 MPQ가 아니라 bwextract가 뽑은 것만 —
   **955개 16MB**(묶으면 6.9MB)다. 갈래별로 `arr` 116K · `scripts` 40K · `triggers` 8K ·
   `Tileset` 2.3M · `unit` 13M. 앞의 넷만으로는 안 돈다(재 봤다): OpenBW가 `images.dat`가
   가리키는 `unit/**/*.grp`를 **머리말 때문에** 연다 — 그림을 그리려는 게 아니라 개체의
   테두리 크기를 거기서 읽는다. 소리·영상·초상화는 한 바이트도 안 쓴다.

(법률 자문이 아니다. "읽기는 되고 뿌리기는 안 된다"는 선은 이 바닥에서 오래 지켜져 온
관행이고, 위 다섯 줄은 그 선 안쪽에 머물기 위한 실무 조치다. 판단과 책임은 운영자 몫이다.)

### 서버 파이프라인 (붙일 자리)

지금은 등록할 때 **브라우저 워커**가 `.rep`을 읽어 트랙을 굽고 그것을 저장한다
(`replaySummaryWorker` → `POST /api/game-results/:id/unit-tracks`). OpenBW는 그 굽는 일을
서버로 옮긴다:

```
업로드된 .rep  →  bwdump <자료폴더> <rep>  →  트랙으로 접기  →  저장
```

* `bwdump`는 리눅스 정적 바이너리로 빌드해 서버에 둔다(의존성이 없어 그대로 된다).
* 브라우저 쪽 분석은 **폴백으로 남긴다** — 서버가 못 돌 때와 옛 저장본을 위해.
* 백엔드 코드는 이 저장소에 없다. 붙이는 자리는 `/api/game-results/:id/unit-tracks`를
  받는 그 서비스다.

### 마지막으로 뚫은 것 — 리마스터의 유닛 태그와 **그릇 크기**

명령이 가리키는 유닛을 못 찾아 **고르기가 늘 빈손**이었다. 그러면 명령은 다 실행되는데
아무 일도 안 일어난다.

옛 태그는 `(index+1) | (generation << 11)`인 16비트였다. 리마스터는 32비트로 넓히면서
index 칸을 **13비트**로 늘렸다:

```
리마스터 태그 = (index + 1) | (generation << 13)
```

처음에는 여기에 `+1700`을 더해야 맞는 줄 알았다. 아니었다. 그 1700은 **그릇 크기 차이**다.

#### LMTS — 리마스터는 한도를 두 배로 늘렸다

요즘 리플레이(1.21+)에는 `LMTS`라는 구획이 있고, 그 안에 그릇 크기가 그대로 적혀 있다.
`xxd`로 읽어 보면 uint32 일곱 개다:

| 그릇 | 리마스터(LMTS) | OpenBW(1.16.1) |
|---|---|---|
| 이미지 | 10000 | 5000 |
| 스프라이트 | 5000 | 2500 |
| thingy | 1000 | 500 |
| **유닛** | **3400** | **1700** |
| 총알 | 400 | 100 |
| 명령(order) | 4000 | 2000 |
| 안개 스프라이트 | 1000 | — |

브루드워는 유닛 자리 번호를 `그릇크기 − 몇째로 만들어졌나`로 매긴다. 그래서 그릇이
1700칸이면 첫 유닛이 1699번, 3400칸이면 3399번이다 — **모든 번호가 정확히 1700씩 어긋난다.**
내가 억지로 더하던 `+1700`이 바로 그 차이였다.

이걸 상수 보정으로 때우면 유닛이 1700칸을 넘는 순간(무한 지도는 미네랄 덩이만 1556개다)
번호가 한 바퀴 돌아 어긋나기 시작한다. 그래서 보정이 아니라 **그릇을 3400칸으로 넓히는**
쪽으로 고쳤다(`bw_limits`, 요즘 리플레이일 때만).

같이 넓혀야 하는 곳이 하나 더 있다 — 엔진 **속**에서도 유닛을 16비트 id로 가리킨다
(수송선 탑승 명부 `loaded_units`, 길찾기의 `last_collision_unit`, 단축키 묶음). 그쪽
index 칸이 11비트라 1700을 넘는 번호가 잘린다. `unit_id_t`에 index 폭을 매개변수로 주고
내부용은 13비트짜리 32비트 id를 쓰게 했다.

**어떻게 알아냈나.** 같은 지도(UGL 17 Anti-Hack)의 1.16 판과 리마스터 판을 나란히 돌려
태그 차이가 늘 7844(= 1700 + 3·2048)임을 보고 식을 세웠다. 그 뒤 리플레이마다 적중률이
시간이 갈수록 무너지는 것을 쫓다가, 못 찾은 태그의 index가 **1041~1755**로 우리가 가정한
범위(1701~3400) 아래라는 것을 보고 규약이 아니라 그릇이 문제임을 알았다. `LMTS`가 그것을
확인해 주었다.

공식 문서에는 이 식이 없다 — screp·jssuh 같은 파서는 태그를 **읽어 넘기기만** 하지 그것이
어느 유닛인지는 안 따지기 때문이다(그럴 필요가 없다). 시뮬레이터만이 이걸 알아야 한다.

### 진짜 원인 — **팀전인데 동맹을 안 걸고 있었다**

리마스터 판이 시간이 갈수록 무너지고 1.16 판만 멀쩡한 것을 두고 오래 헤맸는데, 비교
자체가 잘못돼 있었다. 가진 1.16 리플레이는 **게임 갈래 2(멜리)**, 리마스터 다섯 판은
전부 **게임 갈래 15(Top vs Bottom)** — 즉 "리마스터 대 레거시"가 아니라 **개인전 대 팀전**이었다.

팀전은 같은 편끼리 **동맹으로 시작한다.** OpenBW의 리플레이 설정은 그걸 안 걸어서, 우리
시뮬에서는 한 편이 서로 적이었다. 그래서 만나자마자 아군끼리 치고받았고 — 없던 전투다 —
죽는 유닛이 달라지자 유닛 자리(슬롯) 재활용이 어긋나고, 그 뒤 명령이 통째로 헛돌았다.
"3분 반까지는 완벽하다"던 것은 그저 **양 편이 아직 안 만났을 뿐**이었다.

고침(`replay.h`): 갈래 11·12·13·15면 같은 편끼리 `alliances`와 `shared_vision`을 건다.
시야 공유도 필요하다 — 안 걸면 8인전이 56.3%에서 33.6%로 떨어진다.

| 리플레이 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 151231 (1.16 · 멜리 5인) | 99.7% | 99.7% |
| 251108 (3v3) | 58.6% | **99.9%** |
| SG_26081613330800 (2v2) | 55.5% | **99.9%** |
| SG_26081623590300 (3v3) | 53.1% | **99.9%** |
| DJKisoo (3v2 · 24분) | 29.1% | 82.8% |
| Super빠른무한 BT (4v4 · 31분) | 24.4% | 56.3% |

### 발키리 로켓 문턱도 한도를 따라간다 — 이건 1.21.3이 고친 진짜 버그였다

`create_bullet`에 발키리 로켓만 걸리는 붙박이 문턱 `active_bullets_size >= 80`이 있다.
원판 총알 그릇 100칸의 8할이다. 리마스터 그릇은 400칸이니 문턱도 320이어야 한다.
80으로 두면 발키리가 실제보다 덜 쏴서 그 판의 전투가 갈린다 — 발키리가 나오는 24분짜리
판에서 78.0% → 82.8%.

이건 그냥 상수 하나가 아니라 **원판의 알려진 버그**다. 1.16에서는 지도에 총알이 100발
있거나 발키리 총알이 80발 있으면 발키리가 총알을 못 만들어 **공격이 그냥 안 나갔다**.
리마스터 1.21.0이 스프라이트·총알 한도를 올리고 1.21.3이 총알을 400으로 두 배로 만들면서
이 버그가 사라졌다. 실제로 우리 판에서 발키리가 쏘기 시작할 때 살아있는 총알이 63~91발이라,
한도를 안 올리면 계속 막히는 자리였다.

### 남은 것 — 긴 무한 판 두 개

`DJKisoo`는 16분까지, `Super빠른무한 BT`는 11분까지 **분마다 100%**다. 그 뒤로 무너진다.
씨앗은 아주 작다 — 우리가 유닛을 0.2~2초 늦게 만들거나, 1.6초 일찍 죽인다. 자리와 세대는
정확히 같으니 **구조가 아니라 시각**이 어긋난다. 한 번 어긋나면 생산 명령이 튕기고
(`build:고른게없다`) 눈덩이가 된다: 늦는 양이 12분 5초 → 13분 56초 → 15분 98초로 커진다.
유닛·스프라이트·이미지·총알·명령·thingy 그릇은 하나도 안 찬다(계수기로 확인).

### 어디까지 믿을 수 있나 — 두 신호를 함께 본다

`bwdump`는 늘 두 가지를 센다.

1. **고르기 적중률** — 리플레이 명령이 가리킨 유닛 태그를 시뮬이 찾아내는 비율.
2. **겨냥 어긋남** — 우클릭·표적명령에는 표적 태그와 **그때의 좌표**가 함께 실린다. 사람은
   유닛 그림 위를 찍으므로 그 좌표는 실제 게임에서 그 유닛이 있던 자리다. 우리 시뮬이
   아는 자리와의 차이가 곧 밀림이다. 건물·중립은 그림이 커서 가장자리만 찍어도 수십 픽셀이
   나므로 잣대에서 뺀다. **멀쩡한 판은 90분위가 52픽셀을 안 넘는다.**

둘 다 **두 분 잇달아** 나빠야 갈린 것으로 본다(적중률 97% 미만, 또는 겨냥 90분위 120픽셀
초과). 한 분만 나쁜 것은 큰 전투다 — 방금 죽은 유닛을 가리키는 명령이 몰리면 적중률이
잠깐 떨어졌다가 돌아온다. 한 분만 보는 문턱은 **23분 내내 멀쩡한 1.16 판을 갈렸다고
잘못 읽었다**(그 판의 못 찾은 태그는 전체 26건이고 전부 6~13프레임 전에 죽은 유닛이었다).

### 작은 오차 하나가 눈에 보이기까지 — 잠복 44~108초

`BWDUMP_KICK=<프레임>`은 그 프레임에서 난수를 딱 한 번 더 뽑아 흐름을 한 칸 민다.
그렇게 만든 오차가 '자리 90분위 차이 60픽셀'이 되기까지 걸린 시간을 여덟 지점에서 쟀다:

조합으로 돌아간다. 그 자체가 버그는 아니고, 버그를 **깨우는 방아쇠**다.

### 다음에 쓸 자 — **세대 차이**가 원인 쪽을 바로 가리킨다 (`BWDUMP_SLOT`)

난수 시퀀스를 원판과 맞대는 길은 우리에게 없다 — 리마스터는 후킹할 수 있는 대상이 아니라
리플레이 파일 하나로만 만나는 블랙박스다. 그런데 **맞댈 필요가 없다.** 원판의 세대가
리플레이 안에 이미 적혀 있다.

리플레이의 태그는 `(자리+1) | (세대<<13)`이다. 세대는 그 자리가 재사용될 때마다 하나
오르므로

    리플레이 세대 − 우리 세대 = 그 자리에서 우리가 원판보다 유닛을 몇 번 더(+)/덜(−) 만들었나

가 된다. **부호와 크기까지 나오는 값이다.** 게다가 자리(위치)로 재면 어긋남이 눈에
띄기까지 44~108초가 걸리는데(위 KICK 실측) 세대는 그 자리가 **다음에 골라지는 순간**
드러난다. 난수 호출 수는 대개 원인이 아니라 결과다 — 이쪽이 원인 쪽이다.

```
BWDUMP_SLOT=auto ./bwdump <자료> <리플레이.rep>      # 권장 — 한 번만 돌린다
```

미스가 난 자리만 골라, 그 칸에 우리가 무엇을 언제 넣고 뺐는지 명부로 낸다:

```
  ★ 자리 1741 — 첫 미스 833.0초(프레임 19833) · 4회
     원판 세대 12 · 우리 세대 13 · 차이 -1  → 우리가 그 자리에 유닛을 **더** 만들었다
     들어옴   721.4초  세대12  종류 34 임자2  태그…
     나감     804.9초  세대12  종류 34 임자2  태그…
     들어옴   810.8초  세대13  종류 30 임자0  태그…      ← 원판에 없던 유닛
```

그 한 줄의 **종류**가 곧 첫 갈림의 정체다. 자리를 빠르게 갉아먹는 것부터 의심한다 —
컴샛 **스캐너 스윕** · 스캐럽 · 인터셉터 · 스파이더 마인 · 브루들링 · 알.

**예측 하나** — 위의 고스트·은신·핵 몰림이 "표지"가 아니라 인과일 수 있다. 고스트가 있는
판에는 컴옵스가 있고, 은신을 잡으려면 **스캔을 뿌린다.** 스캔은 유닛으로 태어났다 사라지므로
자리 회전율을 확 올린다. 스캔 하나가 더/덜 만들어지면 그 자리의 세대가 즉시 어긋나고, 그
자리를 물려받은 진짜 유닛의 태그가 안 풀린다. 즉 **"고스트가 낀 판이 갈린다"가 아니라
"스캔이 많이 뿌려진 판이 갈린다"**일 수 있다. 첫 미스 자리의 명부에 Scanner Sweep이
있으면 확정이고, 없으면 그 종류가 다음 자리를 알려 준다.

다른 쓰임:

```
BWDUMP_SLOT=<번호>   그 자리 하나만 실시간으로 (BWDUMP_FIRSTMISS이 알려 준 값)
BWDUMP_SLOT=all      모든 자리를 실시간으로 (크다 — 유닛 하나에 두 줄)
```

### 남은 그림 — PRNG 상태 어긋남

지금까지 잰 것을 종합하면 기전은 이렇다.

1. 리플레이는 결정론적 락스텝이다 — 초기 씨앗과 명령만 있으면 같은 결과가 나와야 한다.
   씨앗은 정확히 읽는다(파일 이름의 유닉스 시각과 일치). 씨앗을 1만 틀리면 무너지는 **모양이
   다르다**(1분 만에 39%로 곤두박질) — 우리 것은 그 모양이 아니다.
2. **난수를 딱 한 번 더 뽑게 만들면 44~108초(중앙 75초) 뒤에 자리가 눈에 띄게 벌어진다**
   (`BWDUMP_KICK`으로 여덟 지점에서 실측). 갈리는 판들은 예외 없이 그 전까지 분마다 100%이다가
   한 순간에 무너진다 — 이 모양과 정확히 같다.
3. 그러므로 남은 것은 **드문 상황에서 난수를 한 번 더/덜 뽑는 자리** 하나를 찾는 일이다.
   자주 쓰이는 갈래(길찾기 산개 50·51, iscript 3·5·7 따위) 안의 희귀 분기일 가능성이 높아,
   "처음 쓰인 시각"으로는 안 잡힌다(해 봤고 안 잡혔다).

다음에 해 볼 만한 것:
 · 가장 일찍 갈리는 판(SG_26072822162900, 8분)을 잡고 씨앗 창(7.1~8.1분)의 프레임을
   하나씩 좁혀 들어간다. 뒤질 구간이 가장 작다.
 · 난수 갈래별 **프레임당 호출 수**를 기록해 두고, 갈리는 판과 같은 지도·같은 빌드의 깨끗한
   판과 곡선을 맞대어 튀는 지점을 찾는다.
 · 길찾기 충돌(`pathing_collision_counter`, `lcg_rand(50)` 분기)의 조건을 하나씩 바꿔 보며
   갈리는 시각이 **뒤로** 밀리는 변형을 찾는다(앞으로 밀리는 것은 전부 오답이다).

| 실행 시점(지연) | `BWDUMP_LAG` −16~+16 쓸기 | 0이 최선 |
| 난수 씨앗 | 헤더에서 읽은 값 = 파일 이름의 유닉스 시각 | 맞음. 씨앗을 1만 틀리면 1분 만에 39%로 곤두박질 — 무너지는 **모양이 다르다** |
| 일시정지·네트워크 지연·색 전환 | 여섯 판의 명령 갈래 목록 | `0x10`·`0x11`·`0x55`·`0x5f`·`0x66` 은 **한 번도 안 나옴** |
| F5(리마스터↔레거시 그림) | — | 화면 설정이라 명령으로 안 나감 |
| 트리거 | `BWDUMP_TRIG` | 승리 판정 몇 번뿐, 사실상 안 돎 |
| 그릇 넘침 | `create_unit`·`create_sprite`·`create_image` 실패 계수 | 한 번도 안 막힘 |
| 전투 | 죽음 수와 대조 | 죽음 6기짜리 판이 1분 만에 66%로 무너짐 — **무관** |

## 트랙 뽑기 — 앱이 먹는 꼴로

```
node scripts/openbw-tracks.mjs <리플레이.rep> [--out 트랙.json] [--step 3]
```

`bwdump --tracks`가 프레임마다 유닛의 자리·방향·상태를 내고, 스크립트가 그것을 앱의
`SimTrack` 꼴로 접는다. 상태 번호는 앱과 같다(0 가만 1 이동 2 안에 탐 3 사라짐 4 싸움
5 채취 6 파묻힘 7 미네랄 들고 8 가스 들고).

키는 **곧게 가는 동안 안 적는다** — 직전 표본이 '적은 점 → 지금'을 잇는 선에서 얼마나
벗어나는지 보고 벗어날 때만 꺾임점을 남긴다. 그냥 다 적으면 14분짜리가 240만 줄인데
19만 줄로 줄고, 레거시 시뮬이 내던 12만 개와 같은 급이다. 곱기는 `BWDUMP_DEV`(픽셀)와
`BWDUMP_HEAD`(0~255)로 조절한다.

지도가 놓아 준 자원(미네랄·가스)은 트랙에서 뺀다 — 앱은 그것을 지도에서 그리고, 경기

## 앱에 붙였다 — 브라우저 시뮬을 걷어냈다 (2026-08-20)

서버가 등록·재분석 때 뒤에서 구워 `game_result_motion_tracks`에 넣고,
`GET /api/game-results/:id/unit-tracks`가 사건 표(`data`)와 함께 `motion`으로 준다.
브라우저는 **풀어서 읽기만** 한다(`src/utils/openbwTracks.ts`).

걷어낸 것 — `ReplayMotionPlayer`에서 178줄:

* `legacy/simClient`의 워커 적재·IndexedDB 캐시·지형/편 지문 열쇠 — 통째로.
* 발사·피격 사건(`shotsAt`·`hitsAt`) — 옛 시뮬이 제 전투 판정으로 내던 것이다.
  참값 자취에는 '누가 누구를 쐈나'가 없어(덤퍼가 아직 안 뽑는다) 트레이서와 피격 불티는
  렌더 제 교전 판정으로 돌아갔다.
* 앱 묶음에서 시뮬 워커 청크가 사라졌다.

**폴백은 없다**(주인 결정) — 사건 표나 참값 자취 중 하나라도 없으면 재생기는 아무것도
안 그리고 "재생할 수 없는 게임이에요" 한마디만 띄운다. 여태는 없으면 명령에서 유추한
그림이라도 띄웠지만, 그건 실제로 벌어진 일이 아니었다.

### v2 사건 표에 아직 남은 몫

참값 자취가 이긴 것: 자리 · 방향 · 상태 · 정체 · 태어남 · 죽음.
v2가 아직 혼자 대는 것:

| 몫 | 덤퍼가 뽑을 수 있나 |
|---|---|
| 로스터(이름·종족·개인색·팀) | 리플레이 헤더에 있다 — 뽑을 수 있다 |
| 체력·실드 변곡점 | 프레임마다 있다 — 쉽다 |
| 인터셉터 수 | 있다 |
| 업그레이드·기술 완료 시각 | 있다 |
| 마법 좌표 | 오더·불릿에서 나온다 |
| 미니맵 핑 | 있다 — 게임 상태는 아니지만 **명령 `0x58`**이라 덤퍼가 이미 지나간다 |

마지막 줄이 관건이었다. 핑은 화면 조작이라 게임 상태에 안 남지만, 덤퍼는 명령 스트림을
통째로 읽으므로(`bwdump_action`) 지나가는 자리에서 좌표만 적으면 된다. 실제로 한 판을
`BWDUMP_RESOLVE`로 열어 보니 `88(0x58)`이 38회 찍혀 있다.

**곧 v2 표는 통째로 없앨 수 있다.** 브라우저가 리플레이를 파싱할 이유가 하나도 안 남는다.

지금은 v2가 그림의 **뼈대**이기도 하다(재생기가 `ents`를 훑고 태그로 자취를 찾는다).
그래서 v2가 못 알아본 유닛은 참값 자취에 있어도 안 그려진다 — 뼈대를 자취 쪽으로
옮기는 것이 다음 정리다.

## 자료 올리기 — 수동이다, 한 번만

자동이 될 수가 없다. 이 자료는 **주인 기계의 스타크래프트 설치본**에서 뽑은 것이라 서버가
스스로 구할 데가 없고, 저장소에도 이미지에도 안 담기로 했으니 배포 아티팩트에도 안 실린다.
자료를 가진 기계에서 한 번 밀어 넣는 수밖에 없다. 볼륨은 한 번 채우면 재배포에도 남는다.

1. 서버에 `OPENBW_BOOTSTRAP_TOKEN`을 채워 배포한다(영문·숫자로 — HTTP 헤더로 간다).
2. `scripts/openbw-upload.sh https://<서버> <토큰>`
3. `OPENBW_BOOTSTRAP_TOKEN`을 **비우고 다시 배포한다.** 문이 닫힌다(빈 값이면 404다).

받는 쪽은 `stargayte-api/src/app/domain/game_results/openbw_bootstrap.py`다. 볼륨 밖을
가리키는 이름이나 심볼릭 링크가 하나라도 있으면 한 파일도 안 쓰고 통째로 거절하고, 이
파일들을 돌려주는 길은 없다(쓰기 전용).

실제 6.9MB 묶음으로 끝까지 확인했다 — 955개가 깔리고, 틀린 토큰은 404고, 그 볼륨으로
덤퍼가 돌아 트랙이 나온다.

### 대소문자 — 맥에서 안 드러나고 리눅스에서 터진다

`images.tbl`은 그림 이름을 `Zerg\Hive.grp`처럼 적어 두는데 뽑힌 파일은 `unit/zerg/Hive.grp`다
(폴더는 소문자, 파일은 원래 대소문자). 맥은 대소문자를 안 가려서 그대로 열렸고, 운영
(리눅스)에 올리고 나서야 `자료 파일 없음: /data/bwdata/unit/Zerg/Hive.grp`로 터졌다.

덤퍼가 자료 폴더를 한 번 훑어 **소문자 색인**을 만들고 그것으로 찾는다(955개라 몇 ms다).
시험은 맥에서 대소문자를 가리는 디스크 이미지를 만들어 한다:

    hdiutil create -size 64m -fs "Case-sensitive APFS" -volname bwcase -quiet bwcase.dmg
    hdiutil attach -mountpoint ./cs bwcase.dmg && cp -R tools/openbw/data/* ./cs/

그 볼륨에서 돌린 결과가 평소 볼륨과 한 바이트도 안 달라야 한다.

## 진단 손잡이 (환경변수)

전부 `bwdump`에 환경변수로 준다. 참값이 어긋날 때 **어디가 틀렸는지** 좁히는 데 쓴 것들이고,
그대로 남겨 둔다 — 다음에 또 어긋나면 같은 순서로 좁히면 된다.

| 변수 | 무엇을 보나 |
|---|---|
| `BWDUMP_RESOLVE` | 분마다 고르기 적중률(찾음·슬롯만) — **시뮬이 아직 실제 게임과 같은가** |
| `BWDUMP_FIRSTMISS` | 처음 못 찾은 태그 몇 개를 자세히 |
| `BWDUMP_MISSTAGS` | 못 찾은 태그 전부(`MISS<탭>태그<탭>프레임`) |
| `BWDUMP_ANYGEN` | 세대 검사를 끄고 자리만 본다 — 자리가 틀린지 세대가 틀린지 가른다 |
| `BWDUMP_GEN` | (우리 세대 → 리플레이 세대) 짝과 분별 차이 |
| `BWDUMP_WHY` / `BWDUMP_WHEN` | 생산 명령이 어느 관문에서 막히나 · 처음 막힌 순간들 |
| `BWDUMP_PEAK` | 그릇(유닛·총알·스프라이트·이미지·명령·경로·thingy) 최고치 |
| `BWDUMP_ORD` / `BWDUMP_RNG` | 명령·난수 갈래마다 처음 쓰인 시각 — 갈리는 시각과 대조한다 |
| `BWDUMP_SLOT` | **자리 칸(index)의 생애 명부** — 세대 차이로 "우리가 유닛을 몇 번 더/덜 만들었나"를 바로 잰다(아래) |
| `BWDUMP_KILL` | 첫 죽음 30건(피가 0이면 맞아 죽은 것) |
| `BWDUMP_TRIG` | 트리거가 도는가 |
| `BWDUMP_ALLY` / `BWDUMP_SETUP` / `BWDUMP_SEED` | 게임 갈래·편·동맹 · 설정 · 난수 씨앗 |
| `BWDUMP_LAG` | 명령 실행 시점을 앞뒤로 민다(0이 맞다는 것을 확인했다) |
| `BWDUMP_DEV` / `BWDUMP_HEAD` | 트랙 키를 얼마나 곱게 남길지 |
| `BWLIM_*` / `BWHALO` | 그릇 한도·발키리 문턱을 하나씩 되돌려 본다 |
| `BWDUMP_CHK` | 지도(.chk)를 파일로 뺀다 |

## (지난 기록) 막혔던 자리

**한 판이 끝까지 돈다.** 13분 26초 경기가 1.5초에 완주하고, 리플레이가 말하는 것과 시뮬이
읽은 것이 전부 맞는다:

| 항목 | 리플레이 | 시뮬이 읽은 값 |
|---|---|---|
| 지도 이름 | New Super◆빠른무한 | 같음 |
| 끝 프레임 | 13:26 | 19196 (= 13:26) |
| 사람 여섯 | 이름·자리 | 전부 같음 |
| 종족 | T·Z·T·P·Z·T | 시작 유닛이 그대로 |
| 시작 미네랄 | 50 | 50 |
| 지도 유닛 | .chk가 1650개 선언 | 1644개 세움(+시작 지점 6개는 소비) |

명령도 다 실행된다 — 우클릭 4578 · 고르기 3358 · 단축키 4107 · 생산 983 · 건설 272.

### 막힌 한 자리 — 고르기가 아무도 못 집는다

명령이 가리키는 유닛 태그를 시뮬이 못 찾는다. 그래서 선택이 늘 비고, 선택이 비니 생산도
건설도 이동도 **하나도 일어나지 않는다**(유닛 수가 800초 내내 시작 그대로다).

숫자로 좁힌 자리:

* 첫 고르기(프레임 2)의 태그는 `0x26cd`·`0x26ce`처럼 **잇따른 값**이다 → 낮은 비트가
  index인 것은 맞다(한 사람의 일꾼 넷이 잇따라 만들어졌다는 뜻).
* 11·12·13비트 어느 폭으로 갈라도 index는 **1741**로 같다.
* 그런데 우리 시뮬의 유닛은 index 0~1699에 있고, 첫 일꾼들은 index 22~25다.
* 지도가 선언한 유닛 1650 + 시작 유닛 38 = 1688로도 1741에 못 미친다 — 실제 게임은
  그 앞에 **쉰 남짓을 더** 만들었다는 뜻이다.

곧 **유닛을 만드는 차례가 실제 게임과 어긋난다.** OpenBW가 옛 리플레이를 제대로 재생하는
것을 보면 옛 게임과는 맞는 차례이므로, 리마스터가 시작 때 무언가를 더 만들거나 다른
차례로 만든다고 보는 것이 옳다. 1v1 리플레이에서도 똑같이 막히므로 지도 크기 문제는 아니다.

다음에 볼 것:
1. 리마스터가 시작 때 더 만드는 것이 무엇인가 — 라바·맵 공개용 유닛·시작 지점 처리 차례.
2. 32비트 태그의 index/generation 나눔이 옛것과 정말 같은가(0x26cd는 옛 규약의 유효
   범위 밖이다 — 세대 4의 유효 구간이 8193~9892인데 9933은 그 밖이다).
3. 옛 형식 리플레이 한 판을 구해 대조 — 지금 막힌 것이 리마스터 탓인지 아닌지 단번에 갈린다.
